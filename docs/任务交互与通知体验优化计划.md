# 任务交互与通知体验优化计划

## 1. 目标

让用户在任务系统中始终清楚三件事：

1. **现在需要我做什么**；
2. **我刚做的操作是否已经生效、下一步由谁处理**；
3. **关键事情发生后，能否一键回到正确的位置完成处理**。

本计划覆盖主目标、子任务、指派、确认/审批、进度、完成、日报及相关通知。目标不是增加更多提醒，而是减少寻找入口、猜测状态和重复填写的成本。

## 2. 现状与核心问题

| 用户感受 | 根因 | 后果 |
| --- | --- | --- |
| “我不知道现在该处理什么。” | 待接收、待审批、待变更确认埋在不同列表和二级入口；首页默认是主目标总览。 | 高优先级待办被遗漏。 |
| “我点了指派，到底成功了吗？” | 直接生效、对方确认、上级审批共用相近入口和文案。 | 用户误以为责任已转移。 |
| “通知点进去又找不到原来的事。” | 推送/站内信未统一携带可解析的目标和操作上下文。 | 用户需搜索、筛选，甚至放弃处理。 |
| “任务创建和日报都很累。” | 创建字段一次性暴露；日报逐项重复填写、缺少批量和复用。 | 临时事项漏记、日报质量下降。 |
| “日期和状态说得不一致。” | 开始日期只影响展示，不是实际可执行状态；完成和 100% 进度也未形成自然闭环。 | 用户对任务是否该做、是否结束没有把握。 |

## 3. 体验原则

1. **行动优先**：默认呈现待我处理、逾期、今日截止，而不是信息总览。
2. **状态可解释**：每个关键操作后，明确展示“已发生什么、下一步是谁、何时提醒”。
3. **通知可行动**：通知必须能直达具体对象，并尽可能提供安全的一键操作。
4. **低频能力不挡路**：配置、导入、周期规则等管理能力与日常执行入口分层。
5. **渐进填写**：先让用户完成意图，再补充治理字段；不要把正式建档成本施加到每次快速记录。
6. **以事件为中心而非页面为中心**：同一事件在列表、详情、助手和系统推送中的文案、状态和跳转一致。

## 4. 目标用户旅程

### 4.1 打开任务模块：30 秒确定优先级

将当前首页改为“行动中心”，按以下顺序展示：

1. 待我决策：待接收、待指派审批、待变更审批；
2. 需要关注：逾期、今天截止、被退回、阻塞；
3. 今日执行：今天正在进行、可补日报；
4. 主目标：作为规划和复盘入口，而不是默认入口。

每个区块展示数量、最紧急的一至三项和“查看全部”。主目标、已完成、未来计划使用次级 Tab 或筛选入口。

**验收标准**

- 用户首次进入无需点击二级图标，即可看见全部待自己处理的事项。
- 待接收、待审批、待变更三类事项分别有数量和明确文案。
- “今日”仅展示与今天存在执行关系的任务；未来任务归入“计划中”。

### 4.2 快速创建：先记录，再治理

提供两个入口：

- **快速新建**：标题、截止日期（可选）、执行人（按权限）；保存后允许继续完善。
- **完整创建**：保留优先级、分类、验收标准、附件、起止日期等字段。

若主目标只能由创建人负责，字段应显示为“创建人即负责人”，不要呈现无法点击的“负责人”选择器。默认分类必须清晰可见，且不能让用户在不知情时被错误归类。

创建成功后不强制打断用户跳转详情；使用“已创建，可继续完善 / 查看详情”的轻提示和撤销能力。只有创建子任务时，才建议回到父任务上下文。

**验收标准**

- 快速创建可在最少两项输入内完成。
- 用户可在提交前明确知道负责人、截止日期、是否需要审批。
- 创建成功后，用户可选择留在当前上下文或进入详情。

### 4.3 指派与审批：把路径说清楚

在选择执行人后、提交前展示状态路径卡片：

| 当前规则 | 提交后的即时状态 | 下一步 |
| --- | --- | --- |
| 直接指派 | 已指派给某人 | 对方开始执行 |
| 需接收确认 | 待对方接收 | 对方接受或拒绝 |
| 需上级审批 | 待某位审批人审批 | 审批通过后变更负责人 |

操作完成页和通知使用同一套描述。审批人或执行人可直接在通知/待办卡片中执行“接受、拒绝、通过、驳回”，高风险操作保留二次确认和备注输入。

需要支持撤回尚未处理的指派/变更；一旦存在待处理变更，冻结会冲突的编辑、完成、删除操作，或使用版本冲突提示。

**验收标准**

- 指派提交后，发起人能立即看到实际状态和下一责任人。
- 每个待处理请求都有可达的独立入口，且可筛选、可计数。
- 接受、拒绝、审批、撤回都通知发起方及受影响负责人。

### 4.4 执行与完成：让 100% 成为可理解的闭环

区分以下状态：计划中、待接收、待审批、进行中、阻塞、待验收、已完成、已取消。

- 到达开始日时自动从“计划中”转入“进行中”；开始前不应出现在“今日执行”。
- 用户将进度更新到 100% 时，询问“标记完成”或“仅表示工作完成，等待验收”。
- 完成按钮应出现在任务卡的主要动作区，而非只在详情深处；尚未达到完成条件时说明缺少什么。
- 已完成父目标不允许继续直接添加子任务；如确需继续，先执行“重新打开”。
- 评价和复盘应在完成/验收后开放，不应与执行动作并列诱导提前评价。

**验收标准**

- 未来任务不能被误操作为执行中或完成。
- 100% 进度不会留下状态仍为进行中的“假完成”任务。
- 所有终态任务的后续操作有明确规则和提示。

### 4.5 日报：记录变化，而不是重填清单

日报页默认只展示“今天有变化”或“需要补充”的任务，其他任务折叠。提供：

- 沿用上次的下一步；
- 批量标记“无进展”；
- 从任务卡一键带入日报；
- 只填写总体进展，不重复填写所有子任务；
- 明确区分任务进展、阻塞和其他工作。

主目标与子任务的汇报需避免互相排斥：负责人可选择汇报目标总体推进，执行人可汇报子任务；统计层面应明确去重规则，避免进度重复计算。

日报提醒应包含“今天尚未填写什么”和直达当天日报的链接；补交窗口、请假免填、非工作日状态都应在首页和通知中一致展示。

**验收标准**

- 日报任务较多时，用户只需处理有变化的条目。
- 主目标存在子任务时，负责人仍有合理的总体汇报方式。
- 提交日报后，同步进度、完成状态和提醒状态一致可见。

## 5. 通知与交互事件设计

### 5.1 统一事件模型

每个业务动作产生不可变事件，至少包含：

```text
eventId            幂等键
eventType          如 assignment_requested / assignment_accepted
taskId             任务 ID
parentTaskId       主目标 ID（如有）
actorUserId        操作人
recipientUserId    接收人
action             可执行动作集合
deepLink           直达页面和上下文
occurredAt         事件发生时间
```

事件首先与任务状态变更同事务落入 outbox，再由异步投递服务发送站内信、实时消息和系统推送。消费者用 `eventId` 去重，失败可重试并可追踪投递状态。

### 5.2 事件—对象—动作矩阵

| 事件 | 接收者 | 通知主文案 | 直达页 | 可操作动作 |
| --- | --- | --- | --- | --- |
| 指派请求 | 执行人 | “某某邀请你接收任务” | 任务确认页 | 接受、拒绝、查看 |
| 指派审批 | 审批人 | “某某提交了任务指派，等待你审批” | 审批卡 | 通过、驳回、查看 |
| 指派结果 | 发起人、原/新负责人 | “指派已通过/被拒绝” | 任务详情 | 查看、重新指派 |
| 任务变更请求 | 审批人 | “任务截止日/负责人发生变更” | 变更对比页 | 通过、驳回 |
| 变更结果 | 发起人、负责人 | “变更已生效/被驳回” | 任务详情 | 查看 |
| 被退回或阻塞 | 负责人、协作人 | “任务需要处理：原因……” | 任务详情 | 更新进度、回复 |
| 即将逾期 | 负责人、必要时负责人上级 | “今天截止，当前进度 X%” | 任务详情 | 更新进度、申请变更 |
| 日报提醒 | 填报人 | “今日日报待填，含 X 条任务” | 当天日报 | 填写 |
| 日报评论 | 日报作者 | “某某评论了你的日报” | 对应日报评论区 | 回复、查看 |

不使用“您有一条新消息”这类无上下文通知。通知落地后，必须精确定位任务、日报日期和待执行动作，不依赖用户再次搜索。

### 5.3 通知频控与降噪

- 同一任务在短窗口内的多次进度更新合并为一条摘要。
- 截止提醒只在关键节点发送：例如提前 1 天、当天上午、逾期后；用户可配置接收偏好。
- 任务详情内实时查看时，不额外推送同会话消息，更不能因此自动标记用户未真正看见的消息为已读。
- 站内未读以“用户实际进入对应任务/日报并看见事件”为准，而不是仅进入任务模块。

## 6. 实施分期

### P0：消除漏办与状态误解（1–2 个迭代）

1. 首页增加显式“待我处理”区块、数量和直达入口。
2. 修复待接收任务、待变更审批任务的列表可发现性。
3. 指派/审批前后展示真实流程和下一责任人。
4. 补齐接受、拒绝、审批、评论、日报等关键结果通知。
5. 推送携带统一 deep link；客户端从通知直接打开正确任务或日报。
6. 仅在实际可见的会话/详情页标记已读。

**P0 发布门槛**：任何待本人处理的任务，在首页、待办列表和通知三条路径中至少有两条可达；一次点击通知即可定位至正确对象。

### P1：缩短高频操作路径（2–3 个迭代）

1. 上线快速新建与完整创建两种模式。
2. 完善“计划中 → 进行中 → 待验收/完成”的状态机。
3. 处理 100% 进度与完成状态的闭环。
4. 提供撤回指派/撤回变更及冲突冻结策略。
5. 日报支持折叠无变化任务、沿用下一步和批量无进展。
6. 首页增加逾期、今日截止、高优先级等快捷筛选。

### P2：可靠性与管理体验（持续优化）

1. 落地事务 outbox、投递重试、事件幂等和投递监控。
2. 建立通知偏好、频控、聚合策略和静默时段。
3. 将配置、导入、周期任务等低频能力迁至“管理”空间；日常用户只看与权限相关的入口。
4. 为管理者提供团队待办、日报完成率、卡点和逾期趋势，而非单纯任务列表。

## 7. 技术改造边界

### 后端

- 任务状态、确认/审批记录和 outbox 事件使用同一数据库事务。
- 所有异步通知由统一投递器消费，不在请求处理器中以无重试 goroutine 直接发送。
- 写操作增加乐观版本号或条件更新，避免待变更期间被静默覆盖。
- 为任务、审批、日报评论提供稳定的事件类型和 deep-link contract。
- 增加通知投递状态、失败原因、重试次数和死信观察能力。

### Flutter 客户端

- 以统一 `TaskRouteContext` 解析 deep link：任务详情、审批卡、接收确认、日报日期和评论锚点。
- 将未读逻辑与“实际可见内容”绑定，不以模块级页面是否打开作为已读条件。
- 抽取状态标签、动作按钮、通知卡片的统一映射，避免同一状态在首页、详情和助手中语义不一致。
- 对快速创建、指派、完成、日报建立埋点，识别高摩擦环节。

## 8. 验收指标

| 指标 | 基线 | 目标 |
| --- | --- | --- |
| 待本人处理事项的漏办率 | 发布前统计 | P0 后下降 50% |
| 从通知到正确对象的成功率 | 发布前统计 | ≥ 98% |
| 指派后用户误判“已生效”的反馈 | 发布前统计 | P0 后下降 70% |
| 快速创建完成时长 | 发布前统计 | 中位数 ≤ 20 秒 |
| 日报提交完成时长（任务较多用户） | 发布前统计 | P1 后下降 30% |
| 任务 100% 但未完成的存量 | 发布前统计 | P1 后接近 0 |
| 通知发送失败但无重试的事件 | 发布前统计 | P2 后为 0 |

## 9. 测试与灰度清单

### 必测场景

- 创建主目标、创建子任务、直接指派、需确认指派、需审批指派。
- 审批通过/驳回、执行人接受/拒绝、发起人撤回。
- 待变更期间编辑、完成、删除、重复提交的冲突处理。
- 未来开始、今天开始、逾期、完成、重新打开等状态迁移。
- 通知离线、重复投递、失败重试、点击系统推送、点击站内信。
- 助手页、任务详情页、日报页切换时的未读标记。
- 有子任务的主目标、跨负责人任务、请假/周末/补交日报。

### 灰度方式

1. 先向一个部门启用行动中心和统一通知跳转；
2. 对比该部门与对照组的漏办、日报耗时、指派审批耗时；
3. 收集高频用户访谈，重点验证“是否知道下一步”和“是否能从通知直接完成”；
4. 指标稳定后逐步启用快速创建、状态机和日报简化。

## 10. 本次评审建议

先确认三项产品决策，再进入开发：

1. 指派到底采用“直接生效、接收确认、上级审批”中的哪些规则，是否按组织/任务类型配置；
2. 100% 进度是否等同于完成，还是必须经过验收；
3. 主目标和子任务在日报、进度和考核中如何避免重复计算。

这三项确定后，P0 的信息架构、事件协议和前后端接口可以一次性定稳，避免后续反复改通知文案和状态逻辑。

| 主目标已具备关闭条件时，任意 PATCH 都可能重复触发“可关闭”提醒 | 5.1 的不可变事件、eventId 幂等和状态迁移触发条件 |
| 缺少任务—通知—跳转—已读的端到端测试 | 8、9 的指标、必测场景和灰度流程 |

### 实施提醒

事件矩阵在开发前应补充三类事件：`progress_milestone_reached`、`task_completed`、`task_evaluated`。所有事件都必须定义接收者、是否合并推送、deep link、可执行动作和幂等键，避免“数据库状态有变化但用户没有得到可行动反馈”。
